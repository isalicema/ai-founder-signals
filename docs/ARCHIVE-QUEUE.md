# 收藏队列：feed 之后那一半

> **这份也是写给 agent 执行的。**

## 这个接缝在解决什么

Feed 只负责**发现**——每天把值得一看的访谈摆到你面前。真正的深读、提炼、归档，
它不做，也不该做。

点「◇ 深看」时**只写一个时间戳**（`archive_requested_at`），零成本、不阻塞、不等待。
真正的深度分析放到你有空、有上下文的时候批量做。

```
feed 点「◇ 深看」  →  队列  →  你（或你的 agent）深读并归档  →  回写已归档
```

⚠️ **仓库只提供队列和取正文，不提供"归档到哪里"。** 那取决于你用什么记笔记
（Obsidian / Notion / 纯文件都行），所以这一段留给你自己接。

---

## 三条命令

```bash
afs queue list              # 列出待处理：标题、人物、公司、链接、标记时间
afs fetch <item-id>         # 取该条的完整正文（会复用仓库已有的抓取能力）
afs queue done <item-id>    # 归档完回写，从队列消失
```

`afs fetch` 会按信源类型自动选路：**YouTube 取字幕、播客取 show notes、网页抓正文**，
所以你不需要另装一套提取器。输出里带 **provenance 标注**，见下。

---

## 给 agent 的执行说明

用户说「处理收藏队列」时：

1. `afs queue list` 取待办
2. 逐条 `afs fetch <id>` 拿正文
3. **完整读完**再写。长内容要读到底，不能只看开头就下笔
4. 写成结构化笔记存进用户的笔记系统
5. `afs queue done <id>` 回写

### 写笔记的三条质量标准

> **不是读后感，是精髓提炼。**

- **核心提炼要能替代原文**：读完这部分等于读完原文精华。技术内容保留具体做法、
  数据结构、关键名词；方法论内容保留框架、决策逻辑、对比
- **不省略重要细节**：数字、来源、具体案例、反直觉结论都要留。
  **不写「有很多数据支撑」这种空话**——那等于没写
- **关联要具体可操作**：结合用户实际在做的事说清楚"所以我该怎么办"，
  **不写「值得参考」「很有启发」这种废话**

判断标准很简单：读完你的笔记，用户应该能回答**「我还需不需要去看原文」**。

### ⚠️ provenance：写之前先看你手上是什么

`afs fetch` 的正文标题里会标明来源类型，**必须据此调整措辞**：

| | 是什么 | 怎么写 |
|---|---|---|
| `视频字幕转写` | 真实对话内容，可能有断句错误 | 可以引述观点，按语义理解错别字 |
| `⚠️ show notes` | **节目方撰写的说明与大纲，不是对话实录** | 能说明「这期会谈什么」，说不了「实际谈出了什么」。**不要写成受访者的第一人称**；写不出具体判断就如实概括议题范围，不要为了显得具体而编造 |
| `网页正文` | 文章原文 | 正常处理 |

这条不是文风讲究。**拿节目方写的大纲冒充"他说了什么"，是在制造读者无法核验的假信息**
——而这个系统不保存原文，事后连核对的机会都没有。

### 管线摘要只是参考

`afs fetch` 会附上管线生成的那段 150-250 字摘要。那是**用来决定要不要点开**的，
不是深读结论。写笔记时以正文为准，不要基于它二次加工——否则是在摘要的摘要上做摘要。

---

## 这个队列还能怎么用

`archive_requested_at` 只是数据库里一个时间戳，消费方式完全自由：

- **别的 agent**：不必是 Claude Code，任何能跑 shell 的 agent 都行
- **定时批处理**：每周日把攒下的一起处理
- **导出**：`afs queue list` 的输出直接喂给别的流程
- **不用队列**：`afs fetch` 也可以直接对任意 item id 用

我们自己接的是 Obsidian 收藏夹——那是我们的用法，不是这个设计的一部分。
